
# Deployment Guide

This guide documents the validated local, MySQL, Docker, Streamlit, and optional Hugging Face/GenAI deployment paths for the Customer Risk Intelligence Platform.

The production model is a deployment-oriented refit of the established research architecture. It is separate from the held-out research evaluation and does not replace the frozen research evidence.

---

## Local

### 1. Prepare the Python environment

Use Python 3.12 and create/activate the project virtual environment.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

### 2. Install dependencies

```powershell
pip install -r requirements.txt
```

### 3. Place the dataset

Place the Telco Customer Churn dataset at:

```text
data/raw/telco_customer_churn.csv
```

The expected source dataset contains 7,043 rows and 21 columns.

### 4. Train the production artifact

Run the training script from the project root using module execution:

```powershell
python -m scripts.train_production_model
```

This creates the deployment-oriented calibrated Random Forest artifact under `models/`.

The production configuration uses the same established research architecture:

- 300-tree Random Forest
- `random_state=42`
- Balanced class weighting
- Sigmoid probability calibration
- 5-fold cross-validation

The production artifact is separate from the held-out research evaluation.

### 5. Score the customer dataset

```powershell
python -m scripts.score_customers
```

This produces:

```text
data/processed/customer_risk_scores.csv
```

The scoring output contains:

- Calibrated churn probability
- Calibrated risk level
- Revenue at risk
- Revenue risk score
- Retention priority score
- Retention priority
- Deterministic retention recommendation

### 6. Set up MySQL

The validated local database environment is MySQL 8.4.

Run the database schema and supporting scripts using MySQL Workbench or the MySQL client:

```text
sql/01_schema.sql
sql/03_views.sql
sql/04_research_summary.sql
```

These scripts create the project database structure, views, and established research-summary metrics.

### 7. Load customer data into MySQL

Run the project-native customer loader from the project root:

```powershell
python -m scripts.load_customers_to_mysql
```

The loader:

- Validates the source columns
- Converts numeric fields
- Handles numeric `TotalCharges` conversion
- Derives the established research features
- Upserts customer records into MySQL

The validated database contains 7,043 customer records.

### 8. Load persisted risk scores into MySQL

After running the customer scoring step, load the persisted risk scores:

```powershell
python -m scripts.load_scores_to_mysql
```

This stores the production-refit customer risk scores in:

```text
customer_risk_scores
```

The score-loading process uses the processed scoring file generated by `scripts.score_customers`.

### 9. Configure the MySQL connection

The application should use the dedicated MySQL application account rather than the `root` account.

The validated application user is:

```text
cri_user
```

Configure the connection through environment variables:

```text
MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_USER=cri_user
MYSQL_PASSWORD=<your-local-cri-user-password>
MYSQL_DATABASE=customer_risk_intelligence
```

Use `.env.example` as the configuration template where appropriate.

Do not commit real database credentials to the repository.

### 10. Run Streamlit

From the project root:

```powershell
streamlit run app/streamlit_app.py
```

The application supports two scoring data sources.

#### CSV mode

```text
CSV
 ↓
Customer CSV
 ↓
Production calibrated Random Forest
 ↓
Customer risk scoring
 ↓
Streamlit dashboard
```

In CSV mode, the application reads the customer CSV and scores customers using the production model artifact.

#### MySQL mode

```text
MySQL
 ↓
Persisted customer risk scores
 ↓
Streamlit dashboard
```

In MySQL mode, the application loads persisted customer risk scores from MySQL and does not rescore the customers.

The Streamlit application includes:

- Risk Overview
- Individual Customer Scoring
- Retention Command Center
- Research Evidence
- Revenue-at-risk information
- Retention-priority information
- Optional SHAP explanations where the required customer features are available

## MySQL

The validated project database is:

```text
customer_risk_intelligence
```

### Core tables

```text
customers
customer_risk_scores
retention_actions
research_summary
```

### Views

The SQL view script creates the customer-level risk view and retention-priority summary view.

The database layer is used to persist production customer and risk outputs and to support application-level querying.

It does not modify the established held-out research evaluation results.

### Database permissions

The Streamlit application should use the dedicated application user:

```text
cri_user
```

The application should not require the MySQL `root` account during normal operation.

## Docker

The repository includes Docker configuration for the MySQL and Streamlit services.

Start the services with:

```bash
docker compose up --build
```

### Expected service endpoints

```text
Streamlit: http://localhost:8501
MySQL:     localhost:3306
```

### Docker reproducibility note

The current Docker Compose setup initializes the database service and schema, but it does not automatically recreate the complete populated 7,043-customer production scoring state used in the validated local environment.

For a full reproduction of the populated database, execute the project-native customer and score loading steps after the MySQL service is available:

```powershell
python -m scripts.load_customers_to_mysql
python -m scripts.load_scores_to_mysql
```

This keeps database population explicit and avoids hiding data-loading side effects inside container startup.

The exact Docker database initialization behavior should be verified before treating the Compose configuration as a fully automated production deployment.

## Hugging Face / GenAI

The GenAI layer is optional and sits on top of the deterministic risk and retention pipeline.

Configure the optional environment variables:

```text
HF_TOKEN=<your-token>
HF_MODEL=<optional-model-name>
```

When configured, the application can use the Hugging Face layer for business-friendly explanations or retention messaging.

Without these variables, the platform uses a deterministic, business-safe fallback explanation.

The GenAI layer does not replace or modify:

- The tabular churn model
- Calibrated churn probability
- SHAP explanations
- Revenue-at-risk calculations
- Retention-priority calculations
- Deterministic risk segmentation

The GenAI layer is an explanation and communication component, not the core churn prediction model.

## Research and Production Separation

The repository intentionally distinguishes the held-out research evaluation from the production refit.

### Research evaluation

```text
Held-out research evaluation
        ↓
Established research evidence
        ↓
Research metrics and conclusions
```

### Production deployment

```text
Full customer dataset
        ↓
Production model refit
        ↓
Calibrated production artifact
        ↓
Customer scoring
        ↓
MySQL / Streamlit
```

The production refit is intended for deployment and application use.

It must not be presented as a replacement for the established research evaluation metrics.

Research metrics should not be silently replaced by production-refit metrics.

## Operational Notes

- The Telco Customer Churn dataset is a static snapshot.
- Production use would require periodic retraining and monitoring.
- Revenue at Risk is an expected exposure measure, not guaranteed lost revenue.
- Historical churn capture does not prove that an intervention prevents churn.
- Retention recommendations are decision-support heuristics, not causal treatment effects.
- Database credentials must remain outside version control.
- Hugging Face credentials must remain outside version control.
- The `.env` file must not be committed to the repository.
- The `.env.example` file should contain placeholders rather than real credentials.
- Model performance, calibration, data quality, and data drift should be monitored in a real production environment.
- The production artifact and research evidence should remain separately documented.
